# HomePlayer 播放引擎阶段 5 实施记录

本文记录“精确 seek、打开体验与恢复”的逐条目实施状态。设计契约仍以《播放引擎架构设计》为准；每个条目独立提交，未完成的项目不视为已经支持。

长稳与硬件验收矩阵按当前实施决策后置，等整个引擎的功能完成后再集中执行，不在本阶段穿插 2 小时或 8 小时 soak。

## 条目 1：Native 音频样本级精确 seek

实施内容：

- 保留从定位点向后解码并丢弃目标前数据的方式，不再按整帧丢弃所有 `PTS < target` 的音频。
- 将 seek 目标直接换算到当前音频帧的采样率时间基。目标落在帧中间时，按 packed/planar 样本布局偏移输入指针，只把目标及之后的样本交给重采样器。
- 音频 priming 继续由 FFmpeg 默认解码路径处理；本条目没有启用需要应用手工处理 `skip_samples` 的解码模式。
- PCM 事件显式携带 Epoch，输出层同时校验事件 Epoch 与当前 Epoch，避免旧时间线回调在 seek 后被误写进新音频缓冲。

验证：

- 新增真实 AAC-LC/MP4 回归，媒体在测试时生成，不提交视频文件。目标为 501 ms，落在 1024 样本 AAC 帧中间。
- 修改前首段 PCM 相对目标偏移 1728 个样本（36 ms）；修改后在一个正弦周期内测得偏移为 0，通过不超过 4 个样本的断言。
- `dotnet test tests/HomePlayer.Playback.Tests/HomePlayer.Playback.Tests.csproj --configuration Release`：37 项通过。
- `dotnet test HomePlayer.slnx --configuration Release`：Core 241、Playback 37、Library 53，全部通过。

边界：

- 当前证据覆盖 48 kHz 单声道 AAC-LC 和既有 PCM 回归，不外推为所有音频编码、采样率和声道布局已完成 priming 矩阵验收。
- open GOP、字幕重建、音视频字幕统一预滚动、异常时间戳和其他阶段 5 项目仍待后续条目实施。
- 本条目只验证解码后的 PCM 时间对齐，不代表已经测得声卡实际发声或目标帧实际显示时间。

状态：Native 音频样本级精确 seek 已完成，后续继续拆做阶段 5 的其余条目。

## 条目 2：seek 后 ASS 字幕重建

实施内容：

- 播放控制器增加统一的 `SeekStarted` 通知，手动 seek、续播定位、返回开头、单集循环和播完后重播均通过同一入口触发。
- 音轨切换可能引发 Native 内部 seek，也会触发字幕重建通知；不支持的引擎仍可自行忽略空操作，不据此声明所有音轨切换都会重建解码时间线。
- 播放器在 seek 开始时立即清除 ASS 当前位图、缓存和 libass 滤镜图，下一次按目标时间渲染时使用新实例。SRT/PGS 继续通过既有随机时间查询，不重读字幕文件。
- ASS 渲染任务增加代际校验，Reset 或来源变化前排队的迟到任务不得重新写回旧位图。字幕延迟加入渲染键，调整延迟造成的时间跳变同样重建滤镜图。

验证：

- 新增控制器回归，覆盖手动 seek 和播完后重播的 `SeekStarted` 通知。
- `dotnet test HomePlayer.slnx --configuration Release`：Core 241、Playback 38、Library 53，全部通过。
- `dotnet build src/HomePlayer.App/HomePlayer.App.csproj --configuration Release`：0 警告、0 错误。

边界：

- 本条目验证控制通知、状态隔离和真实 App 构建，未执行 ASS 特效字幕的视觉帧哈希矩阵；复杂特效的视觉回归仍需后续图像验收。
- 统一预滚动尚未实现，ASS 重建不表示音视频与字幕已在同一预滚动边界恢复。

状态：seek 后 ASS 字幕重建已完成，后续继续处理精确 seek 的其他边界。

## 条目 3：open GOP 精确 seek 像素验收

实施与验证：

- 保持既有 `av_seek_frame(..., AVSEEK_FLAG_BACKWARD)`、从定位点向后解码和丢弃目标前帧的实现；真实媒体回归未发现需要修改定位代码的问题。
- 新增测试时生成的 H.264/MP4，显式启用 open GOP、25 帧 GOP、3 个连续 B 帧和 B 帧参考。
- 分别从文件开头顺序解码和直接 seek 到 1040 ms，强制两条路径使用软件 BGRA 输出。两者目标 PTS 相同，64×48 帧的全部 BGRA 字节完全一致。
- `dotnet test HomePlayer.slnx --configuration Release`：Core 241、Playback 39、Library 53，全部通过。

边界：

- 当前证据覆盖单个 H.264 开放 GOP 样本的软件 BGRA 路径，不代表所有编码、容器、硬解路径和损坏索引已经完成矩阵验收。
- 像素一致验证的是解码交付帧，不是 SwapChain 实际显示帧；实际呈现观测层级仍按既有诊断定义区分。

状态：open GOP 的当前代表性场景已通过精确 seek 像素验收，后续继续统一预滚动和异常时间戳工作。

## 条目 4：Native 播放中 seek 的统一预滚动

实施内容：

- 播放中 seek 不再立即重启媒体时钟。目标视频帧到达 Scheduler 后先标记视频就绪，首段新 Epoch PCM 写入音频输出后标记音频就绪，两者齐备才释放本次预滚动。
- Native 播放引擎在 seek 时暂停 WASAPI 并清理旧缓冲；`SeekPrerollReady` 触发后先恢复音频输出，再重启媒体时钟并交付目标视频帧，避免音频和视频分别从各自解码完成时间恢复。
- 预滚动状态按 Epoch 隔离，连续 seek 不会由旧音频或旧目标帧释放新时间线。暂停 seek 不恢复音频输出；预滚动中暂停会明确结束本次等待，后续播放不重复等待旧状态。
- seek 到 EOF 没有目标帧或新 PCM 时，通过 EOF 路径完成预滚动，保留既有 decoder/output drain 和 Ended 语义，不因等待就绪而卡死。

验证：

- 新增真实 AAC 回归，验证顺序为“新 Epoch PCM → 一次 SeekPrerollReady → 目标视频帧”，并检查恢复前不会交付目标帧。
- AAC 样本级裁剪、open GOP 像素一致、100 次连续 seek、暂停 seek 和正常 EOF 回归保持通过。
- `dotnet test HomePlayer.slnx --configuration Release`：Core 241、Playback 40、Library 53，全部通过。
- `dotnet build src/HomePlayer.App/HomePlayer.App.csproj --configuration Release`：0 警告、0 错误。

边界：

- 当前统一预滚动覆盖 Native 播放中 seek；LAV/DirectShow 仍由滤镜图管理自己的恢复过程，未套用 HomePlayer 的二次调度。
- 验证观测到 PCM 写入和目标帧交付顺序，不把该顺序当作声卡实际发声或屏幕实际扫描时间；音画同步漂移仍由后续真实设备与长稳验收测量。

状态：Native 播放中 seek 的音视频统一预滚动已完成，后续继续异常时间戳修复。

## 条目 5：Native 异常时间戳修复

实施内容：

- 新增流级 `MediaTimestampRepair`，保留正常起始 PTS 和 VFR 时长；缺失 PTS 时按上一帧结束位置合成，缺失时长使用当前帧信息、流帧率或上一帧时长。
- 向后回绕和超过 5 秒的向前 discontinuity 会平移到预期时间线，后续帧沿用偏移；Epoch 变化时清空修复状态，正常 seek 不被误判为 discontinuity。
- 按容器 `start_time` 建立媒体相对起点，保留音视频之间的相对偏移，避免非零起始时间导致首帧被长时间延迟。
- 音频解码器显式使用流 `pkt_timebase`。音频修复在该时间基进行，seek 裁剪再换算到采样率时间基，不再假设所有音频流都以采样率为时间基。

验证：

- 确定性测试覆盖缺失 PTS、时长回退、VFR、33 位式回绕、前向跳变和 Epoch 重置。
- 真实 Annex B H.264  elementary stream 没有容器时间戳，前四帧 PTS 严格递增且时长为正。
- 真实 MP4 使用 5 秒 `output_ts_offset`，首帧落在媒体相对起点 0–100 ms 内。
- 既有 AAC 样本裁剪、统一预滚动、open GOP、100 次连续 seek 和 EOF 回归保持通过。
- `dotnet test HomePlayer.slnx --configuration Release`：Core 245、Playback 42、Library 53，全部通过。
- `dotnet build src/HomePlayer.App/HomePlayer.App.csproj --configuration Release`：0 警告、0 错误。

边界：

- 当前 discontinuity 修复策略以单流连续播放为目标，不等同于 ordered chapters 的跨文件 TimelineId；跨文件时间线在后续本地媒体语义工作包处理。
- 真实设备上的 MPEG-TS 回绕、损坏索引和多格式 discontinuity 仍需硬件/媒体矩阵扩充；本条目不虚称所有异常文件都可恢复。

状态：Native 缺失 PTS、非零起点、VFR、回绕和 discontinuity 的统一修复已落地，后续继续 SMB 分级预读与打开体验。

## 条目 6：UNC/SMB 有界探测与播放预读

实施内容：

- 新增 `FfmpegInputProfile`，只把 UNC、`//`、扩展 UNC 和 UNC file URI 识别为网络路径；`\\?\C:\...`、设备路径和本地文件继续使用 FFmpeg 默认配置。
- UNC 输入使用 4 MiB `probesize`、2 秒 `analyzeduration`、1 MiB `buffer_size` 和 5 秒 `rw_timeout`，分别约束流信息探测、分析时间、播放预读和读写等待，不执行无界预读。
- 保留打开、probe、读取和 seek 的 `AVIOInterruptCB` 取消；没有通过关闭后重开来模拟分级缓冲，也没有引入 FFmpeg.AutoGen 未绑定的原生 ABI。

验证：

- 路径与预算测试覆盖普通 UNC、斜杠 UNC、扩展 UNC、UNC file URI、本地盘符、本地扩展路径和设备路径。
- 本地真实媒体打开、播放、seek、EOF 和异常时间戳回归保持通过，确认本地默认 I/O 未改变。
- `dotnet test HomePlayer.slnx --configuration Release`：Core 245、Playback 50、Library 53，全部通过。

边界：

- 当前环境未提供可验证的真实 SMB 共享，因此本条目只完成配置与本地回归，不把 UNC 参数测试写成真实网络吞吐、断网恢复或 SMB 凭据验收。
- `rw_timeout` 是否作用于具体 Windows UNC 协议路径取决于 FFmpeg 实际协议实现；不能用它替代中断回调或真实断网测试。

状态：UNC/SMB 有界探测与预读配置已完成，真实 SMB 行为留待对应环境验收；后续继续下一集预探测与看门狗。

## 条目 7：可取消的下一集预探测

实施内容：

- 当前项打开并开始播放后，后台只读取下一项的轻量 `MediaProbe`，不创建第二个播放会话、不自动播放、不恢复下一项进度，也不改变当前播放列表索引。
- 预探测限制为单任务和 5 秒预算。`FfmpegProbe.Read` 增加 `AVIOInterruptCB` 取消，并复用 UNC 有界配置；停止、切集和新的打开操作会取消旧任务，超时、取消或迟到结果不会写入缓存。
- 新增只读 `Playlist.PeekNextIndex`，随机播放预探测不推进随机游标；随机序列边界无法确定时不猜测下一项。
- 成功结果通过 `NextProbe`、`NextProbePath` 和 `NextProbeAvailable` 提供，只作为下一项信息缓存，不冒充已完成的预打开会话。

验证：

- 控制器回归确认预探测不改变当前项、不增加播放次数，完成后只缓存下一项信息；切集会取消正在等待的探测令牌。
- 随机播放测试确认 `PeekNextIndex` 与实际 `NextIndex(false)` 相同且不消耗顺序；已取消 Probe 不会打开媒体。
- `dotnet test HomePlayer.slnx --configuration Release`：Core 246、Playback 53、Library 53，全部通过。
- `dotnet build src/HomePlayer.App/HomePlayer.App.csproj --configuration Release`：0 警告、0 错误。

边界：

- 本条目是预探测，不是预打开；尚未保留第二个解码器、GPU 帧或 Surface，切集时仍需执行正常 Provider 打开。
- 预探测失败不会阻塞或改变当前播放，真实 SMB 的取消延迟和下一集打开收益仍需对应环境与性能样本验证。

状态：可取消、无副作用的下一集预探测已完成，后续继续看门狗与分级恢复。

## 条目 8：Native 播放进度看门狗

实施内容：

- 新增独立看门狗线程，以帧成功交付和 PCM 成功写入作为进度信号；默认连续 10 秒没有交付进展时触发超时，测试可缩短预算。
- 超时只触发一次：设置 I/O 中断、取消会话队列和线程、停止 Playing，并通过 `Faulted` 报告明确错误。本条目不自动重建 Provider。
- Play 和 Seek 会重置进度起点，暂停时不进行 Playing 超时判定。
- Close 保留未退出线程的句柄并提前返回，后续 Close 可重试 Join；不再出现首次 Join 失败后丢弃句柄、下一次误释放仍在使用的原生上下文的问题。

验证：

- 人为阻塞首帧 `FrameArrived` 回调，100 ms 测试预算内触发“看门狗超时”并停止 Playing；解除回调阻塞后可正常清理。
- 正常打开、连续 seek、统一预滚动、EOF 和异常时间戳回归保持通过。
- `dotnet test HomePlayer.slnx --configuration Release`：Core 246、Playback 54、Library 53，全部通过。
- `dotnet build src/HomePlayer.App/HomePlayer.App.csproj --configuration Release`：0 警告、0 错误。

边界：

- 看门狗只覆盖 Native 已打开会话的交付停滞，不替代打开阶段已有的 15 秒取消，也不监测 DirectShow 内部状态。
- 本条目只实现“取消并进入明确 Failed”，尚未自动执行 Provider 内恢复、跨路线恢复或恢复次数限制；这些在下一分级恢复条目处理。
- 无法退出的托管回调或原生调用仍不会被提前释放；进程隔离在后续安全工作包处理。

状态：Native 进度看门狗已完成，后续继续有界分级恢复。
