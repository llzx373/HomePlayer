# HomePlayer 播放引擎架构设计

## 1. 文档目的与适用范围

本文定义 HomePlayer 下一阶段播放引擎的目标架构和实施契约。目标不是简单增加几个引擎名称，而是在保留现有稳定路径的同时，建立一套可以长期演进、允许用户对比、能够逐步引入 GPU 零拷贝和高级渲染的播放体系。

本文是设计目标，不表示其中能力已经实现。实施时按第 18 节分阶段推进，不把整个重写作为单一版本任务。

本文中的“必须”表示实施和验收的约束，“可以”表示可按实测结果选择的方案。若实现与本文存在偏差，必须先记录偏差、影响范围和替代契约，不能用相同的指标名称掩盖不同语义。

## 2. 核心结论

1. **HomePlayer 自己掌握播放选择层、会话、命令、能力模型、状态迁移、诊断和用户偏好。**第三方引擎只作为可替换的底层提供者。
2. 首版形成两套播放内核：
   - 原生 FFmpeg；
   - DirectShow / LAV。
3. DirectShow / LAV 定位为 Windows 兼容和外部渲染器生态路线。微软已将 DirectShow 标记为 legacy；HomePlayer 的新核心抽象不得依赖 DirectShow 专属模型。
4. DirectShow 内核的视频输出可以替换：
   - HomePlayer Renderer；
   - madVR；
   - 后续可选 MPC Video Renderer。
5. HomePlayer 自有渲染分两级：
   - 基础 D3D11 Renderer，负责稳定、兼容和明确的降级；
   - libplacebo Renderer，负责高级画质。
6. **libplacebo 只替代渲染后段，不替代解封装、解码、时钟、音频和会话。**
7. 帧传输、视频渲染和 Surface 宿主是三个不同维度。不能把 CPU/GPU 帧交付、SwapChain 输出和原生窗口输出混成同一层接口。
8. HomePlayer 的独立 Video Scheduler 只调度 HomePlayer 拥有呈现权的路线。madVR、MPC VR、mpv 等外部输出继续自行调度，HomePlayer 统一其会话和诊断语义，不进行二次调度。
9. Flyleaf 用于研究零拷贝、线程取消、D3D11 和 WinUI 集成，并进行 A/B 对照；是否作为正式 Provider 由实测决定，不作为架构成立的前提。
10. mpv 若以后引入，应同时评估原生窗口和 libmpv render API，不预设它只能使用原生窗口。
11. 插件化指官方维护的完整管线方案，不在第一版开放任意第三方 DLL，也不允许用户任意拼接所有解码器、渲染器和音频组件。
12. 所有新路径都保留明确回退。现有 BGRA 路径在新链路验证完成前不删除。

## 3. 产品目标与非目标

### 3.1 目标

- 默认打开稳定，不依赖用户理解解码器和渲染器。
- 用户可以切换完整播放路线，并比较实际效果。
- 用户已有 LAV、madVR 等环境时，可以利用其优势。
- Native 和 LAV 能逐步共享 GPU 帧模型、能力、字幕、截图和诊断语义。
- 性能结论由统一指标和可重复测试支持，而不是由引擎名称或宣传决定。
- 新能力按文件、设备、当前状态和实际管线动态展示，不出现启用了却无效的按钮。
- 所有时钟、呈现、拷贝和故障指标都能说明观测来源，不把近似值伪装成精确值。
- 不可信媒体、原生依赖和官方插件包都有明确的安全、更新和故障边界。

### 3.2 非目标

- 不在第一版同时内置 FFmpeg、LAV、Flyleaf、mpv、LibVLC、GStreamer、MDK 等全部引擎。
- 不重写 madVR、MPC Video Renderer 或 libplacebo 的全部算法。
- 不把 libplacebo 当作完整播放器。
- 不把 madVR 当作 HomePlayer 的通用 SwapChain Renderer。
- 不要求所有 Provider 共用 HomePlayer 的解码线程、视频调度器或音频渲染器。
- 不在第一版实现任意第三方脚本和插件生态。
- 不用单一 CPU 占用或单个测试文件给引擎做永久排名。
- 不在没有明确产品需求时承诺 DRM/PlayReady、光盘菜单或所有 Dolby Vision 模式的完整支持。
- 不把“调用过 Present”当作“画面已经扫描到屏幕”，也不把“使用硬解”当作“全程零拷贝”。

## 4. 当前实现与主要边界

当前入口是 `PlaybackController.PlayPathsAsync`，默认由 `PlaybackProviderRegistry` 在 LAV 和 FFmpeg 之间选择，并用 `PlaybackSession` 统一 SessionId、Epoch、命令结果和旧帧隔离。两条路径最后仍交付 CPU BGRA `VideoFrame`，再进入同一个 `VideoPresenter`。

### 4.1 原生 FFmpeg 当前路径

```text
avformat_open_input / AVIOInterruptCB
→ avformat_find_stream_info
→ 独立 demux 线程
→ 有界 Packet Queue（数量 + 字节）
→ 独立视频/音频解码线程
→ swscale 转 BGRA / swr 转 PCM
→ 有界 VideoFrame Queue（帧数 + 字节）与有界音频输出
→ HomePlayer Video Scheduler
→ VideoPresenter.Map / CopyFrame
→ D3D11 纹理
→ waitable SwapChainPanel
```

音频由 swr 转成 48 kHz、s16，按当前解码声道数生成默认输出声道布局，经 500 ms 上限的 `BufferedWaveProvider` 交给 WASAPI。PCM 写入具有背压，seek、倍速和关闭可以清理旧输出。声道数不是固定为 stereo，但默认布局仍不等于完整保留源文件的声道掩码和顺序。

视频等待由独立 Scheduler 控制。能够取得 WASAPI `IAudioClock` 时使用设备位置、关联 QPC 和媒体锚点映射主时钟；不可用时明确回退到单调时钟，不再使用“已写音频字节数”近似设备位置。

当前 1080p 软件基准采用分阶段解码配置：首帧使用单线程降低启动成本，第一次 seek 在 Epoch 重建边界升级为 FFmpeg 自动线程，缩短长 GOP 的目标帧解码时间。该配置由同媒体 A/B 数据选择，不外推为所有硬件和内容的最佳值。

demux EOF 会依次执行 decoder、resampler 和 time-stretch drain，等待尾帧调度、托管 PCM 队列清空及 WASAPI `CurrentPadding` 归零后才报告 Ended。`FrameLease` 已包含 PTS、Duration、TimeBase、SessionId、Epoch、TimelineId、FrameSequence、颜色和设备代际。打开、probe、读取和 seek 使用 `AVIOInterruptCB` 取消；UNC 输入另有 4 MiB 探测、2 秒分析、1 MiB 播放预读和 5 秒读写预算，本地输入保持默认。连续 seek 通过 Epoch 清理和入口/出口丢弃隔离旧时间线，Ended 与 seek 的状态更新使用同一状态锁。Native 看门狗连续 10 秒没有完成音视频交付时取消会话并报告 Faulted；线程未退出时 Close 保留句柄且不释放原生上下文。Controller 对当前项最多执行原 Provider 与自动路线两轮恢复，打开失败不跳下一集，超过次数进入明确失败。

Native 当前支持软件 YUV 平面上传（Z2）和同设备 D3D11VA 纹理（Z3），并保留 swscale BGRA（Z1）回退。软解 NV12/P010 和 yuv420p/yuv420p10le 不再必须经过整帧 BGRA 转换；D3D11VA 使用 Presenter 的设备、共享锁和 AVFrame 租约。动态像素格式和分辨率会重建对应资源。

当前仍有以下边界：

- 精确 seek 的视频路径按目标丢弃前序帧；H.264 open GOP 的顺序解码与 seek 目标帧已通过 PTS/BGRA 像素一致回归。Native 音频已支持跨越目标帧的源样本级裁剪，AAC priming 由 FFmpeg 默认路径处理并有真实 AAC 回归，PCM 回调携带 Epoch 隔离旧数据。Native 播放中 seek 会等待目标视频和新 PCM 就绪后统一恢复 WASAPI、时钟与目标帧。Native 已按 Epoch 修复缺失 PTS、非零起点、回绕和 discontinuity，并保持流时间基与 VFR 时长。ASS 在统一 seek 通知后清除缓存并重建 libass，迟到渲染任务按代际丢弃；复杂 ASS 视觉矩阵尚未验收。其他编码/硬解的 open GOP、音频 priming 和异常媒体矩阵仍需持续扩充；
- 动态分辨率已做资源重建，设备代际失效有明确故障语义；自动设备热插拔恢复和原生调用的进程隔离仍需后续阶段完善；
- HDR 支持 Basic 输出转换和回退交换链；Native 源 HDR10 mastering/content-light 元数据已保留并用于交换链，LAV 仍使用回退值。动态 HDR 元数据、真实 HDR 显示器视觉/跨屏验收尚未完成；
- 当前基准覆盖软件 YUV 和 D3D11VA 的解码交付，不能替代真实呈现、4K/HDR、2 小时/8 小时长稳和设备移除测试。

### 4.2 LAV 当前路径

兼容路径仍为 RGB32 Sample → `BgraSinkFilter` → CPU BGRA。GPU 路径为：

```text
LAV Video D3D11 Native
→ IMediaSampleD3D11 纹理 + ArraySlice
→ HomePlayer D3D11SinkFilter
→ 共享纹理句柄 / CPU NV12/P010 降级
→ VideoPresenter
→ waitable SwapChainPanel
```

LAV 自己创建解码设备，因此共享纹理路线报告为 Z4，不冒充同设备 Z3。Sink 同时接受 CPU NV12/P010（Z2），BGRA 回退继续保留。当前逐帧操作仍主要按 `1/fps` 模拟，不能代表所有 VFR、隔行和异常时间戳内容的真实帧边界；P010 硬解尚需按实际设备验证。

### 4.3 当前呈现与指标边界

当前 `VideoPresenter` 支持 BGRA、CPU NV12/P010 和 D3D11 纹理输入。CPU BGRA 使用动态纹理和 `Map/CopyFrame`，YUV 使用独立亮度/色度纹理，GPU 帧直接创建 SRV 或打开共享纹理。交换链已启用 frame-latency waitable object，最大帧延迟为 1；显示输出快照记录当前显示器、SDR/HDR、交换链格式和颜色空间，显示变化时重建交换链。

Controller 的 `playback.first-decoded-frame` 只表示解码帧已交付，不表示完成上传或显示。Renderer 分别记录 `Submitted` 和 `PresentReturned`；后者不命名为 `Displayed`。DXGI Frame Statistics 以独立来源采样记录，Windows 合成和实际扫描时间无法可靠取得时仍为 `Unknown`。常规逐帧诊断默认每 30 帧采样，首帧和 seek 全量记录。

性能工具位于 `scripts/Measure-Playback.ps1` 和 `scripts/Compare-Playback.ps1`，验收预算位于 `scripts/PlaybackPerformanceProfile.json`。对比使用同文件 SHA-256、同操作序列和相同观测语义，统计 P50/P95/P99、失败、取消和 Unknown。

### 4.4 当前 UI 中的路线切换

“打开”下拉菜单已并入“用其他路线打开”，提供 HomePlayer 原生（FFmpeg）与 LAV + HomePlayer。手动指定路线失败时不静默换路线，自动模式才进行有界回退。旧的 `forceFfmpeg` 调用保持兼容，内部统一映射到 `PlaybackRoute`。

当前切换采用 OperationId 和显式先关闭旧会话的降级事务，保存 TransferState 与偏好，失败停留当前项并可重试，连续切换由最新 OperationId 决定；新旧会话并存和失败回滚仍未实现。音轨与字幕偏好已持久化 StableId，优先按容器 UID 和元数据身份恢复，歧义时保留自动选择而不任意选轨。

当前项播放后会对只读下一项执行单任务、5 秒上限的可取消预探测，缓存轻量 `MediaProbe`，不创建或播放第二会话；随机顺序通过只读 Peek 获取，不推进随机游标。

### 4.6 后续工作推荐顺序

后续先补可靠性、时间线和真实设备证据，再扩大高级渲染与外部引擎数量。每项完成后仍应独立提交并更新实施记录。长稳与硬件验收矩阵按当前实施决策后置到整个引擎功能完成之后；现阶段从精确 seek 开始逐项推进。

| 优先级 | 工作包 | 主要内容 | 前置条件与完成门槛 |
|---:|---|---|---|
| 1 | 长稳与硬件验收矩阵 | 2 小时主路线、8 小时发布候选 soak；真实设备移除、驱动重置、显存/句柄/租约趋势、P010、4K/HDR、多屏和 VRR | 阶段 4 代码已就位；所有主路线无持续资源增长，失败可恢复或进入明确 Failed，Unknown 不记作通过 |
| 2 | 精确 seek、打开体验与看门狗 | open GOP、音频 priming、字幕重建、统一预滚动、异常时间戳、SMB 分级预读、下一集预探测和分级恢复 | 原阶段 5；目标帧按约定观测层级验收，覆盖连续 seek、seek 中切集、EOF 和设备故障 |
| 3 | 颜色、HDR 与截图收尾 | 源 mastering/HDR 动态元数据、真实 HDR 输出和跨屏、SDR 字幕合成、GPU 最终帧 Staging 截图 | 颜色帧哈希或容差比较通过；SDR/HDR 截图语义一致，跨屏后无错误矩阵或静默降级 |
| 4 | 路线事务与稳定轨道身份 | prepare/commit/abort、OperationId、可并存检测、失败回滚、稳定音轨/字幕标识和 TransferState | 切换失败不丢失当前播放；连续切换无旧事件、资源泄漏或轨道错配 |
| 5 | libplacebo 高质量输出 | D3D11 后端、性能/平衡/高质量预设、色调映射、去色带、去隔行和高级缩放 | Basic 始终保留；同显示契约和图像回归通过，GPU 耗时与画质分别记录，不以 DPI 推断精度 |
| 6 | 外部渲染器与其他 Provider | madVR/MPC VR 参照、原生窗口能力、截图和字幕限制；按需评估 mpv/Flyleaf | 不接入 HomePlayer 二次调度；airspace、叠层、截图和指标限制明确，A/B 数据证明引入价值 |
| 7 | 本地媒体语义 | ordered chapters/editions、跨文件时间线、外挂音轨、多角度/无缝分支和损坏媒体恢复 | TimelineId 与稳定轨道身份统一；不与基础零拷贝或 HDR 同时扩大范围，降级语义明确 |
| 8 | 进程隔离与供应链加固 | 不可信媒体/字幕隔离、原生看门狗、插件签名/哈希、SBOM、私有依赖加载和敏感诊断规则 | 无法取消的原生调用不得提前释放资源；隔离成本、崩溃恢复和共享纹理 IPC 均有实测 |

## 7. 核心抽象

### 7.1 PlaybackProvider

Provider 表示一套完整播放管线，负责：

- 稳定 ID、显示名称、版本和成熟度；
- 检查当前环境中的可用性；
- 提供声明能力和依赖信息；
- 对指定媒体进行有超时、有资源上限的轻量能力探测；
- 创建播放会话；
- 报告实际 Provider 版本和依赖版本。

Provider 不负责媒体库、播放列表、全局设置和页面布局。能力探测不得自动播放、长时间占用独占设备或无界读取网络文件。

### 7.2 IPlaybackSession 与命令协议

Session 表示一次播放，负责：

- Open / Play / Pause / Stop / Seek / Close；
- 当前生命周期、传输状态、位置、时长和轨道；
- 实际运行能力与管线信息；
- 状态、故障、EOF 和指标事件；
- 当前视频输出和 Surface 限制。

控制层采用命令、事件和只读快照。每个异步命令至少携带：

```text
CommandId
SessionId
Epoch
CommandType
Accepted / Completed / Cancelled / Failed
FailureReason
```

“命令已接受”不等于“命令已完成”。UI 和 Controller 必须能区分：

- 命令已排队；
- 命令已生效；
- seek 目标帧已实际呈现；
- 命令被后续命令取代；
- 命令因状态变化或故障失败。

重复 Stop、Close 和取消必须幂等。迟到的完成、故障、帧和 EOF 事件必须按标识丢弃。

### 7.3 会话标识与时间线标识

- `SessionId`：一次播放会话的全局唯一标识，重新打开文件或切换路线时创建新值。
- `MediaId`：媒体身份，与 SessionId 分离；多文件章节不能只靠当前文件路径表示。
- `Epoch`：同一会话内每次 seek、切音轨、换解码器或其他时间线重建时递增。
- `TimelineId`： ordered chapters、跨文件片段或 discontinuity 的时间线身份。
- `SurfaceGeneration`：Surface 挂载、卸载或重建的代际。
- `DeviceGeneration`：GPU 设备丢失和重建的代际。

这些标识不能相互替代。旧 Session、旧 Epoch、旧 Surface 和旧 Device 的迟到数据都必须有明确丢弃规则。

### 7.4 状态模型

不用一张互斥状态图混合所有概念，而是拆成三个维度。

生命周期：

```text
Closed
→ Opening
→ Ready
→ Closing
→ Closed

Opening / Ready / Closing
→ Failed（保留故障快照，允许按契约 Closing 或重建）
```

Ready 会话的传输状态：

```text
Stopped ↔ Playing ↔ Paused
Playing / Paused → Ended
Ended → Seek / Play / Close（按命令契约迁移）
```

独立的操作与数据状态：

```text
CurrentOperation: None / Seeking / Recovering / TrackChanging
IsBuffering: true / false
```

状态契约必须定义：

- 每个状态允许的命令及并发命令的取消关系；
- Opening、Seeking 和 Recovering 的完成条件；
- seek 或恢复后返回 Playing 还是 Paused；
- Buffering 与 Playing/Paused 可以共存，不单独破坏传输状态；
- 任意状态进入 Closing/Closed 的资源释放顺序；
- 原地恢复、降级恢复和必须重建会话的条件；
- Ended 后 seek、重播和自动连播的位置语义。

### 7.5 帧、渲染和输出抽象

```text
IFrameSource
└─ 输出 CPU/GPU FrameLease，不负责 WinUI 宿主

IVideoRenderer
├─ Basic D3D11 Renderer
├─ Libplacebo Renderer
└─ External Renderer Adapter

IVideoSurfaceHost
├─ SwapChainPanel Host
└─ Native Window Host

ExternalVideoOutput
└─ 外部引擎拥有渲染和调度，通过适配器报告能力和指标
```

不能要求所有 Provider 都输出 BGRA，否则会把零拷贝引擎重新变成 CPU 拷贝管线。也不能要求所有 Provider 都输出 HomePlayer FrameLease，否则无法自然接入自行渲染的完整引擎。

### 7.6 VideoSurfaceHost

WinUI 页面只依赖统一 SurfaceHost，负责：

- 挂载、卸载和清屏；
- 尺寸、DPI、全屏和窗口状态；
- 控件与字幕叠层能力；
- 截图能力及颜色语义；
- 设备丢失、SurfaceGeneration 和恢复；
- 当前显示器和输出能力；
- 当前输出实际限制。

原生窗口输出必须明确报告 airspace、输入焦点、叠层、截图和全屏限制，不能假装与 SwapChain 输出完全一致。

## 8. 能力模型

### 8.1 小接口与能力声明分离

可选能力可以使用小接口实现，例如倍速、逐帧、音频延迟、字幕和截图。页面不直接判断 `engine is SomeEngine`，也不通过反射拼出展示逻辑。

能力状态与能力提供方分开建模：

```text
CapabilityStatus
├─ Supported
├─ Unavailable(reason)
├─ Unsupported(reason)
└─ Unknown

CapabilityOwner
├─ Engine
├─ Application
├─ Renderer
├─ ExternalOutput
└─ None
```

`Unavailable` 不是提供方。原因应同时包含稳定的机器可读 `ReasonCode` 和面向用户的解释文本。

例如截图可以由 HomePlayer Presenter 提供，不要求每个解码引擎重复实现。

### 8.2 声明能力、有效能力和实际观测

能力分三层：

1. **Declared（声明能力）**：Provider 声明理论上支持，用于打开前的初步路线筛选。
2. **Effective（有效能力）**：结合当前文件、设备、设置和会话状态后，当前是否允许执行。
3. **Observed（实际观测）**：本次运行实际使用的解码器、拷贝路径、颜色输出和渲染器。

声明能力示例：是否支持外挂字幕、倍速和原生窗口。

有效能力示例：

- 当前字幕格式是否可渲染；
- 当前文件是否支持精确逐帧；
- 当前显示设备是否支持对应 HDR 输出；
- 当前是否存在可切换音轨；
- 当前输出是否允许包含字幕的最终帧截图。

实际观测示例：

- 当前是否硬解；
- 当前是否发生 copy-back；
- 当前零拷贝等级；
- 当前交换链格式和颜色空间；
- 当前实际渲染器和像素格式。

能力和实际管线变化时发布事件。按钮、菜单和快捷键都通过同一个 Controller 检查。真正执行时仍允许返回 `Unsupported`、`Busy`、`InvalidState` 或 `Failed`，防止查询后状态又发生变化。

### 8.3 页面展示规则

- 常用按钮保留位置，暂时不可用时禁用并解释原因。
- 引擎专属设置在不支持的路线上隐藏。
- 不支持的调用不得空操作或伪装成功。
- `Unknown` 不得显示成 `Supported`。
- 截图能力拆分为源帧截图、最终显示帧截图、是否可包含字幕以及输出颜色格式。

## 9. 数据流、时钟与呈现调度

### 9.1 分阶段数据流

HomePlayer 自有帧输出路线共享以下概念流程：

```text
文件/SMB 字节
→ 可取消 I/O 与预读
→ Probe / Demuxer
→ 带 PTS/DTS 的压缩 Packet
→ 有界 Packet Queue
→ 视频/音频/字幕解码
→ 带时间戳的 Frame/PCM/Cue
→ 有界输出队列与背压
→ 统一时间线
→ 视频处理与字幕合成
→ Renderer
→ SwapChain 或原生窗口
→ Windows 合成
→ 屏幕
```

Native 内核逐步拆清 Source/Demuxer、Decoder、Audio Renderer、Video Scheduler、Subtitle Renderer 和 Presenter 的执行边界。各阶段拥有明确的线程/任务所有权、输入输出类型和取消协议，不再让单个播放循环同时负责读包、解码、等待呈现、音频输出和 seek。

DirectShow 内部继续由滤镜图管理其执行模型，HomePlayer 在 Provider 边界保持相同的会话、时间和诊断语义，不强行把 DirectShow 改成自己的线程模型。

### 9.2 可取消 I/O 与预读

取消必须覆盖整个打开和播放生命周期，而不只覆盖播放循环：

- `avformat_open_input`；
- `avformat_find_stream_info`；
- `av_read_frame`；
- seek；
- 自定义 SMB、缓存和预读实现。

FFmpeg 路径必须使用 `AVIOInterruptCB` 或等价机制中断阻塞调用，并为打开、probe、读取和恢复设置明确超时。取消回调本身不得执行阻塞清理或再次进入同一原生调用。

预读必须有内存、时间和网络预算。下一集预探测或预打开不得自动播放，不得突破用户设置的网络、隐私和资源策略。

### 9.3 主时钟与音频时间线

有音频时优先使用音频设备实际位置作为主时钟，例如 WASAPI 的设备位置与 `IAudioClock`，不以“已写音频字节数”近似代替设备实际播放位置。无音频或音频时钟不可用时，使用明确的单调时钟备用路径。

音频时钟映射至少保存：

```text
AudioDevicePosition
AssociatedQPC / 单调时钟
MediaAnchor + TimeBase
PlaybackRate
输出延迟与缓冲估计
ClockSource 与可信等级
```

必须处理设备位置回绕、暂停、恢复、设备热插拔、倍速、重采样和时钟漂移。不能把设备位置直接等同于媒体 PTS，必须经过锚点和延迟映射。

视频、音频和字幕使用带 TimeBase 的 64 位时间戳。每帧至少保留 `PTS + Duration + Epoch + TimelineId`。跨 TimeBase 和跨文件边界使用明确的整数 rescale 与舍入规则，核心逻辑避免反复使用 double 秒数换算。

Native 音频路径逐步改为：

```text
带时间戳的 PCM Queue
→ 有界预滚动缓冲
→ WASAPI 拉取
→ 音频设备位置与 QPC
→ 媒体时间锚点
→ Master Clock
```

预滚动缓冲必须可快速清空，暂停、seek 和切音轨不应等待旧缓冲自然播放完。时钟模型需要明确处理：

- 输出设备延迟和首次启动校准；
- 暂停、继续、倍速和 seek；
- 音轨切换、采样率与声道布局变化；
- 音频设备热插拔与重新锚定；
- 音画小偏差的渐进校正；
- 音画大偏差时的丢帧、跳音频或重新同步。

小偏差不通过频繁突变纠正，大偏差才允许明显跳变，并记录校正原因与幅度。

### 9.4 有界队列、背压与取消

队列必须同时限制数量和时间/内存预算，而不是只限制 Packet 个数。视频帧队列还要区分 CPU 内存与 GPU 显存预算。

每个阶段具备：

- 背压：呈现或解码变慢时，上游逐步减速；
- 独立取消：seek、切集和关闭不卡在读取、解码或呈现中；
- Epoch 清理：旧时间线的数据在队列入口和出口都能被丢弃；
- 可解释的溢出策略：不能静默丢音频或无限增长内存；
- 资源所有权：队列清空和阶段退出后，所有 FrameLease 都能归还。

丢帧原因必须区分：解码慢、呈现晚、主动跳帧、队列满、seek 清理和设备恢复。

### 9.5 EOF 与 drain

Demux EOF 不是播放结束。EOF 必须按顺序处理：

1. 停止向 decoder 输入新 Packet；
2. 按 FFmpeg 的 send/receive 契约 drain 视频和音频 decoder；
3. drain 重采样器、时间伸缩和其他有内部延迟的处理级；
4. 继续输出带正确时间戳的尾部 Frame/PCM/Cue；
5. 等待视频输出队列中最后一帧按策略呈现；
6. 等待最后一段音频实际播放，而不是只写入缓冲；
7. 再报告 Ended。

若用户停止或取消，则不等待自然 drain，直接进入有界清理流程。

### 9.6 独立 Video Scheduler

仅对 HomePlayer 拥有呈现权的输出使用独立 Video Scheduler：

```text
Decoded Frame Queue
        ▼
Video Scheduler
├─ 根据主时钟选择待呈现帧
├─ 计算 PTS 与目标呈现时间的偏差
├─ 等待 / 显示 / 丢弃 / 重复
├─ 暂停时保留最后一帧
├─ 估计显示刷新周期与下一呈现时间
└─ 记录各观测层级的呈现时间和丢帧原因
        ▼
Basic D3D11 / libplacebo Renderer
```

逐步引入可等待交换链、Present 统计和刷新周期估计，形成精确 frame pacing。Scheduler 必须能回答“究竟是解码慢、提交慢、GPU 慢，还是刷新率不匹配”，而不是仅记录解码线程曾经交出过一帧。

外部渲染器和原生窗口不使用该 Scheduler。它们可以上报自身时钟和统计，但 HomePlayer 不得再次按其 PTS 延迟或重复 Present。

### 9.7 呈现时间的观测等级

所有首帧、seek 和 frame pacing 指标必须标记观测层级：

```text
Decoded             解码完成
Submitted           已提交渲染
PresentReturned     Present 调用已返回
GpuCompleted        已知 GPU 工作完成
Composed            已知 Windows 合成完成
Displayed           有可信依据的实际显示/扫描时间
Unknown             当前环境无法观测
```

`PresentReturned` 不得命名为 `Displayed`。`GetFrameStatistics` 等接口在多显示器、其他全屏应用或特定驱动环境下可能不可靠，指标必须记录来源、可信等级和 `Unknown`，不能用近似值冒充精确值。

### 9.8 打开、seek 与切集

精确 seek 使用两阶段过程：

```text
目标时间 + TimelineId
→ 增加 Epoch 并取消旧操作
→ Demuxer 定位目标之前可正确解码的起点
→ 清空旧 Epoch 队列
→ 从关键帧或必要参考起点解码
→ 丢弃目标之前的音视频数据
→ 处理 decoder priming 和音频预滚动
→ 重建字幕状态
→ 音视频字幕在同一预滚动边界恢复
→ 目标帧实际呈现
```

实现必须覆盖 open GOP、B 帧、音频 priming、目标附近字幕、seek 到 EOF、VFR 和跨文件章节。连续 seek 默认采用“最后一个命令胜出”，旧命令必须可取消且不得完成到 UI。

“seek 命令返回”不等于 seek 完成，性能指标必须测到目标帧在可观测层级呈现，并注明层级。

打开与切集逐步增加：

- 有界 probe：基础流信息足够时先打开，完整媒体分析放后台；
- 后台分析导致流参数变化时，通过动态能力和格式重建处理，不静默切换轨道；
- 大文件、SMB 和慢速磁盘的取消式读取与分级预读；
- 缺失 PTS、VFR、异常时间戳、discontinuity 和时间戳回绕的统一修复策略；
- 下一集预探测或预打开，恢复时不自动播放；
- 条件允许时的低延迟或无缝连播；
- 帧缓存支持真正的上一帧，而不是只用当前位置减 `1/fps` 模拟。

这些优化不得改变观看进度和自动连播的现有安全语义。

## 10. 帧所有权、GPU 同步与零拷贝

### 10.1 FrameLease

统一帧租约至少包含以下公共描述：

```text
CPU 平面或 GPU 纹理描述
格式、宽高、各平面 Stride、Texture Array Index / Subresource
PTS、Duration、TimeBase、Epoch、TimelineId、FrameSequence
色彩矩阵、范围、色域、传递函数、Chroma Location、HDR 元数据
SAR/DAR、裁剪、旋转、镜像、隔行与场序信息
Adapter LUID、DeviceGeneration、共享句柄与同步信息
所有者、Release / ReturnToPool
```

底层 `AVFrame`、DirectShow Sample 或纹理对象由具体 Provider 所有。公共契约可以保存不透明句柄和必要的引用，但不得迫使所有 Provider 暴露同一种原生类型。

租约协议必须明确：

- 是否支持克隆和引用计数；
- 释放是否幂等、是否允许跨线程；
- GPU 使用完成前不得释放或回池；
- 跨上下文/设备使用时 keyed mutex、fence 或其他 acquire/release 协议；
- DeviceGeneration 改变后旧纹理如何处理；
- 队列丢弃、设备恢复和异常路径都能归还租约；
- 帧携带的静态和动态 HDR 元数据可以随帧变化。

### 10.2 零拷贝分级

诊断不得只显示布尔值“零拷贝”，而应记录实际路径：

```text
Z0：GPU→CPU copy-back 后再上传
Z1：无 GPU→CPU 回读，但存在 CPU 整帧格式转换和上传
Z2：CPU 解码，YUV 平面直接上传，无 CPU 整帧 BGRA 转换
Z3：同设备 GPU 解码纹理直接渲染，无每帧 CPU 回读或上传
Z4：跨设备/跨进程共享或复制，额外记录共享和同步成本
```

Z4 不自动等同于 Z3。每条路线都必须能说明是否存在 GPU→CPU 回读、CPU 色彩转换、CPU 整帧上传、跨适配器复制和额外 GPU 拷贝。

### 10.3 Native 零拷贝目标

```text
FFmpeg D3D11VA
→ D3D11 NV12/P010 纹理
→ FrameLease + DeviceGeneration + 同步契约
→ HomePlayer/libplacebo Renderer
→ SwapChainPanel
```

实现必须覆盖 `get_format` 协商、hw device/frames context、格式约束、动态格式变化和 copy-back 回退。软解路径可以上传 YUV 平面到 GPU，不必先通过 swscale 生成整帧 BGRA。

### 10.4 LAV 零拷贝目标

新增独立 D3D11 Renderer/Sink，而不是继续扩张 BGRA Sink：

```text
LAV Video D3D11 Native
→ D3D11 Sample / Allocator
→ GpuVideoFrame / FrameLease
→ HomePlayer/libplacebo Renderer
```

需要按 LAV 实际输出处理格式协商、设备与 Allocator、纹理同步和动态格式变化。优先让解码与呈现使用同一适配器；跨设备共享不作为默认假设。

在大规模实施前必须完成最小技术验证，证明以下内容可工作：

- NV12 样本协商和 Allocator；
- 解码设备与渲染设备一致；
- flush、seek 和动态格式变化；
- Sample/纹理生命周期；
- 设备丢失和资源归还。

不能预设“把 BgraSink 换成纹理”就能完成该路线。

### 10.5 回退顺序

```text
D3D11 Native 同设备零拷贝
→ 可用的 DXVA/共享纹理路径
→ CPU YUV 上传
→ 当前 RGB32/BGRA 路径
```

回退必须写入 PipelineInfo 和 Observed 能力，不能把 copy-back 显示成零拷贝。回退次数和原因应受限制并可诊断，避免每帧在两个路径之间反复切换。

### 10.6 截图

正常播放不为截图额外保留整帧 CPU 副本。需要截图时，再把当前显示纹理复制到 Staging Texture 并回读。

截图契约必须区分：

- 源帧或最终显示帧；
- 是否包含字幕和控件；
- 原始 HDR、色调映射 SDR 或其他输出格式；
- 使用源颜色还是显示器颜色管理结果。

madVR 输出可以在运行时探测 `IBasicVideo::GetCurrentImage` 或宿主集成能力，但不能预设所有版本和模式都支持。不能使用 HomePlayer 的 `_lastFrame` 冒充外部渲染器的最终画面。

## 11. 渲染、HDR 与显示输出

### 11.1 Basic D3D11 Renderer

负责：

- 基础 YUV→RGB；
- 正确矩阵、范围、比例、裁剪和旋转；
- 基础缩放和 Dithering；
- 明确的 SDR/WCG/HDR 输入降级；
- 低资源播放与兼容回退。

Basic Renderer 遇到不支持的位深、颜色格式或 HDR 输出时，必须声明实际降级路径，不能按错误矩阵直接显示。它是所有 HomePlayer 自有帧输出应保留的稳定基线，不要求外部原生输出使用该 Renderer。

### 11.2 libplacebo Renderer

负责高级图像处理：

- Lanczos/EWA 等缩放；
- 线性光与 Sigmoid 处理；
- 色彩管理、ICC/3DLUT；
- HDR 色调映射、峰值检测和色域映射；
- Debanding、Dithering；
- YADIF/BWDIF 去隔行；
- 可选帧混合。

输出尺寸可以影响渲染工作量和缩放策略，但 **DPI 不决定内部数值精度**。去色带、色彩转换、线性化和色调映射的顺序必须遵循算法和画质要求，不能仅因输出尺寸较小就一律后移。动态质量调整应依据 GPU 耗时、格式、算法依赖和预设，不依据 DPI 猜测精度需求。

后续可评估隔行 cadence 检测与 IVTC/反胶卷过带，不能用普通帧混合冒充运动补偿插帧或 IVTC。

libplacebo 支持 CPU 上传和 GPU 输入，使用它本身不等于零拷贝。零拷贝仍由 HomePlayer 的帧传输和同步实现。

首版只暴露少量预设：

```text
性能：libplacebo fast / Basic Renderer
平衡：libplacebo default
高质量：libplacebo high_quality
```

放大算法、去色带、去隔行和帧混合可提供少量用户选项。LUT 尺寸、Sigmoid 参数、场景阈值等底层参数不进入普通设置页。AI 超分和插帧只作为后续独立可选模块评估，不替代基础缩放、去隔行、色彩和时钟正确性。

当前实现只开放 fast/default/high_quality 三档，使用未修改的 libplacebo 7.360.1 私有动态库。BGRA、独立 CPU NV12/P010 和 FP16/BGRA 输出已有真实 D3D11 逐像素回归；HDR10 mastering/content-light 元数据传给渲染器。共享 D3D11 NV12/P010 的双视图输入未通过图像验收，因此 `SupportsInput` 明确选择 Basic，不能返回错误画面或把该路线记作高级渲染。去隔行和帧混合尚无用户入口，不按已完成能力展示。

### 11.3 DisplayOutputInfo 与 HDR 输出契约

HDR 不是单纯的渲染器选项。SurfaceHost 和 Renderer 必须共享当前显示输出快照：

```text
显示器身份与当前窗口所在输出
SDR / WCG / HDR / Auto Color Management 状态
交换链格式与颜色空间
显示器色域、亮度和可用元数据
当前 ICC / 显示颜色管理策略
DisplayGeneration / 能力变化原因
```

实现必须覆盖：

- 8-bit、10-bit、FP16 等交换链格式选择；
- `SetColorSpace1` 和必要的 HDR 元数据；
- 窗口跨屏移动、系统 HDR 开关和显示能力变化；
- ICC 与 Windows 自动颜色管理的关系；
- HDR 视频与 WinUI SDR 字幕、控件的亮度和合成；
- 不支持目标输出时回退到明确的色调映射或 SDR 路径。

输出颜色契约应在阶段 0 定义并完成最小验证，不能等 libplacebo 阶段才首次处理。

### 11.4 madVR / MPC VR

它们是 DirectShow 的独立输出路线，不与 libplacebo 嵌套。其画质、HDR、刷新率和字幕由各自渲染器负责。

madVR 的字幕需要 `ISubRenderCallback`、XySubFilter 或其他宿主字幕路径。madVR 不负责扫描和解析全部外挂字幕。HomePlayer 的 WinUI 字幕和 CPU 截图不能直接复用。

当前 `LAV + madVR` 路线复用同一 `LavPlaybackEngine` 和 DirectShow 会话，只替换输出节点。首版使用独立顶层原生窗口，避免把 HWND 叠入 WinUI；madVR 完全拥有呈现和调度。`IBasicVideo` 提供真实尺寸/帧率，`IMediaSeeking` 提供流位置，连续两次读取到末尾后只通知一次 EOF。实测 madVR 在 EOF 可保持 `State_Running`，因此不强行要求 Stopped。路线不发出 HomePlayer `FrameLease`，零拷贝等级和内部呈现指标为 `Unknown`，WinUI 字幕与最终帧截图明确禁用。

## 12. 音频、字幕与本地媒体语义

音频输出尽可能由独立服务提供，统一：

- 设备选择与热插拔；
- 实际设备时钟和媒体时间锚点；
- 声道掩码、声道顺序、采样率和重采样；
- 音量、静音、倍速和音频延迟；
- underrun 和恢复指标。

使用原生 DirectShow 音频渲染器或引擎自带音频时，通过能力接口描述实际路径，不强求所有引擎共用同一种实现。多声道声道映射与 HDMI 比特流直通作为独立能力处理，直通与软件解码不能混为同一条音频路径。

HomePlayer SwapChain 输出共享字幕服务。字幕契约必须明确：

- seek 和 Epoch 后的 cue 清理与重建；
- ASS 字体附件、字体回退和缺字处理；
- PGS 等位图字幕的颜色空间；
- 字幕在色调映射前还是后合成；
- 源帧截图和最终显示截图是否包含字幕。

原生 madVR/mpv/Flyleaf 输出可以使用各自字幕体系，但需在能力和截图语义中明确差异。

本地媒体语义作为后续独立能力规划，不与基础零拷贝和 HDR 同时开工：

- Matroska ordered chapters 与 editions；
- 多版本、多片段和跨文件章节时间线；
- 外挂音轨及独立音频延迟；
- 多角度、无缝分支的能力识别与明确降级；
- 损坏文件尽可能播放到可恢复位置，而不是一次坏包就终止整个会话。

## 13. 路线选择与状态迁移

### 13.1 三种用户选择

1. **自动（推荐）**：根据媒体、设备、能力和历史故障选择路线，并显示实际选择及原因。
2. **全局默认**：用户固定路线，失败时不静默更换。
3. **单次指定**：“用其他路线打开”，可选择记住此文件，但不默认扩散到整个媒体库。

### 13.2 故障历史与回退策略

自动回退必须限制次数和范围。故障历史键至少包含：

- Provider 及版本；
- 媒体格式或故障相关流信息；
- GPU、驱动和输出设备；
- 故障类型；
- 时间戳和 TTL。

SMB 暂时不可读不能导致路线被永久降权。手动指定路线不被历史自动策略覆盖。每次自动回退都必须告知用户实际变化并记录 Trace。

### 13.3 PlaybackTransferState

切换路线时迁移：

- MediaId、文件、播放列表和当前项；
- 播放或暂停状态；
- 实际呈现进度、目标 seek 进度及其区别；
- 音量、静音和倍速；
- 音轨稳定标识；
- 字幕稳定标识、外挂路径、开关和延迟；
- 音频延迟与画面比例。

轨道稳定标识不能只使用 Provider 内部流索引。应结合 MediaId、容器流 UID、轨道类型、语言、标题、disposition 和必要的回退规则生成，并允许用户确认歧义匹配。

### 13.4 prepare / commit / abort

路线切换按事务处理：

```text
保存 TransferState
→ 创建切换 OperationId，取消旧切换
→ 新会话 prepare（资源允许时）
→ prepare 成功：停止旧会话事件并 commit
→ 释放旧 Surface 和旧会话
→ 恢复轨道与偏好
→ 精确 seek
→ 恢复播放/暂停

prepare 失败：abort 新会话
→ 资源允许时保留旧会话继续播放
```

若 Surface、解码器或独占设备使新旧会话无法并存，必须明确采用“先关闭旧会话”的模式。此时 prepare 失败进入可恢复的停止状态并提供重试，不假装旧会话仍能回滚。

切换过程必须有超时、取消和最后一个 OperationId 胜出规则。手动指定路线失败时提供“重试 / 本次改用其他路线 / 修改默认路线”。

## 14. 插件、安全与依赖管理

### 14.1 官方 Provider 包

第一版只支持官方维护的 Provider 包：

```text
plugins/<provider-id>/
├─ plugin.json
├─ 适配程序集
├─ 私有原生依赖
├─ 依赖清单 / SBOM
└─ 许可证与来源信息
```

Manifest 包含稳定 ID、版本、Playback API 版本、成熟度、平台、声明能力、依赖和文件校验信息。

原则：

- 不强迫不同 Provider 共用同一 FFmpeg。
- 插件损坏或版本不匹配不影响其他路线。
- 第一版不做热卸载。
- 原生依赖使用明确的私有加载路径，避免意外加载系统目录中的不兼容 DLL。
- 任意第三方插件若以后开放，优先使用独立进程和版本化 IPC，避免原生崩溃直接影响主程序。

### 14.2 威胁模型与供应链

不可信媒体、字幕、网络输入和 Provider 包都纳入威胁模型。至少覆盖：

- 恶意或损坏媒体导致原生崩溃和内存破坏；
- 插件包篡改、错误更新和依赖混淆；
- 原生调用卡死且无法安全终止；
- SMB 凭据、完整媒体路径和诊断信息泄露；
- 原生依赖漏洞跟踪、版本更新和回滚。

完整性校验、签名和用户替换是不同概念：

- 官方包可以用签名和哈希证明来源及完整性；
- 用户自行替换受 LGPL 等许可证约束的组件时，应显示不受官方签名支持的明确提示；
- 完整性校验不能用来阻止用户行使其替换 LGPL 组件修改版本的权利。

### 14.3 进程隔离决策

FFmpeg、字幕解析或其他原生组件是否做进程隔离，由以下因素共同决定：

- 不可信输入的安全风险；
- 真实崩溃和卡死数据；
- 共享纹理和 IPC 成本；
- 看门狗能否有界取消；
- 无法取消时是否能安全释放资源。

不能只由性能或崩溃频率决定。若超时原生调用仍在执行，不得直接释放其上下文、纹理或回调所属对象。

## 15. 指标、结构化 Trace 与 A/B 对比

### 15.1 统一指标

统一记录：

- 打开到各观测层级的首帧时间；
- seek 到目标帧各观测层级的时间，并统计 P50/P95/P99；
- 解码、队列、提交和呈现耗时；
- 丢帧数量及原因；
- 音画偏差、校正幅度和音频 underrun；
- 实际解码器、渲染器、像素格式和零拷贝等级；
- 交换链格式、颜色空间和显示输出信息；
- CPU、GPU、显存和非托管内存趋势；
- 连续切集后的资源增长。

每个指标必须带单位、观测来源和 SessionId/Epoch。无法获取时记录 `Unknown`，不以 0 代替。

### 15.2 结构化 Trace 与诊断导出

每次播放生成可关联 SessionId/Epoch/CommandId 的结构化 Trace：

```text
Open
→ Probe
→ DecoderSelected
→ FirstDecodedFrame
→ FirstSubmittedFrame
→ FirstPresentReturned
→ FirstObservedFrame（含观测层级）

SeekStart
→ Flush
→ KeyframeFound
→ PrerollReady
→ TargetFramePresented（含观测层级）

Frame PTS / QueueDepth / DecodeCost / SubmitLatency / PresentLatency / DropReason
AudioDevicePosition / QPCAnchor / AVOffset / Underrun / ResampleCompensation
DeviceGeneration / SurfaceGeneration / DisplayGeneration / RecoveryReason
```

高频逐帧 Trace 应可采样或按级别启用，避免诊断本身改变性能结果。诊断包可以导出事件、版本、实际管线和最近错误，默认不包含完整媒体路径和敏感配置；为复现问题可使用用户明确同意的媒体标识。

### 15.3 可重放与确定性测试

核心逻辑提供虚拟时钟、虚拟音频输出和虚拟呈现器，使暂停、seek、EOF、丢帧和设备变化可以脱离真实硬件做确定性测试。

支持重放命令序列：

```text
打开 → 播放 → seek → 暂停 → 逐帧 → 切音轨/字幕 → 恢复
```

测试体系逐步加入：

- 非法状态命令、重复 Close 和命令幂等；
- 连续 seek、seek 中切集、打开中取消和旧事件迟到；
- 长时间播放、连续切集和设备热插拔；
- 损坏媒体、字幕和解封装输入的隔离进程模糊测试；
- 帧哈希或容差图像比较，验证 seek 和色彩处理没有回退；
- 真实设备上的首帧、seek、音画同步和资源基线。

### 15.4 A/B 对比

对比工具顺序执行各路线，使用同文件、同进度和同一操作序列，区分冷启动与热启动，不默认同时运行多个引擎争用 GPU。

“相同质量档位”只用于相同渲染器的参数比较。madVR、libplacebo、Basic 等路线之间必须分别记录：

- 相同或尽可能等价的画质目标；
- 无法等价的算法和输出差异；
- 性能、画质、同步和兼容性结果。

必要时随机化路线顺序并重复多轮，降低缓存、温度和后台负载偏差。不用单一分数宣布永久优胜。

## 16. 故障恢复与看门狗

需要覆盖：

- 硬解失败后按流回退软解；
- GPU 设备移除、驱动重置和显卡切换；
- 音频设备断开和默认设备变化；
- SMB 暂时不可读；
- 文件播放中被替换或移动；
- 单条流损坏但其他流可继续；
- decoder/resampler drain、EOF 和线程退出；
- 反复创建销毁后的资源回收。

增加分级健康监测：

- Demux/Decoder 长时间无进展；
- Renderer 长时间未提交新帧；
- 音频时钟停止但会话仍报告 Playing；
- 停止、seek 或设备恢复超过规定时限；
- 原生依赖异常退出或失去响应。

看门狗按以下顺序处理：

1. 发起有界取消并记录操作；
2. 禁止该 Session 接收新命令；
3. 尝试当前 Provider 内恢复；
4. 限制连续恢复次数，避免无限重启；
5. 若原生调用未退出，将会话标记为隔离/废弃，不提前释放其仍在使用的资源；
6. 无法安全恢复时保留可用的最后帧、记录结构化故障并进入明确 Failed 状态；
7. 必要时按第 13 节策略重建 Provider，或触发进程级恢复。

跨 Provider 回退遵循第 13 节的选择策略，并保存完整状态。故障历史按版本、设备和 TTL 管理，避免临时故障造成永久路线降级。

## 17. 许可证与商业边界

- HomePlayer 主体源码继续 MIT；这不表示包含第三方组件的完整发行包只受 MIT 约束。
- libplacebo 按 LGPL-2.1-or-later 处理，优先未修改的动态 DLL，保留版本、对应源码、构建方式与第三方声明，不静态并入主程序。
- LAV Filters 按 GPL-2.0 处理。若随包携带，需要同时解决对应源码义务、COM 私有加载和系统版本隔离。
- LAV 使用定制 FFmpeg 时，对应源码和构建资料必须覆盖实际发行的定制版本，不能只提供上游通用链接。
- 动态链接或 COM 私有加载本身不会自动消除 GPL 义务，应按实际集成和分发方式审查。
- MPC Video Renderer 按 GPL-3.0 处理，是否引入由实际集成方式单独评估。
- madVR 闭源，未取得明确再分发授权前只检测用户已安装版本，不打包或代收安装。
- Flyleaf 按 LGPL-3.0-or-later 处理，正式引入前按具体版本、依赖和分发方式单独审查。
- mpv 默认按 GPLv2+ 处理；只有满足条件的构建才按 LGPLv2.1+ 评估。其配套 FFmpeg 和其他依赖仍可能改变最终义务。
- 编解码专利、Dolby 等品牌/认证、用户 Shader 和 LUT 许可证与播放库版权分别处理。
- 每个 Provider 包保留 SBOM、实际依赖版本、对应源码位置和构建说明，发行前执行许可证检查。

## 18. 分阶段实施

实施顺序先保证时间、状态、资源和安全语义正确，再引入 GPU 零拷贝和高级渲染。每个阶段通过对应验收后再扩大范围，不把硬解、HDR、完整字幕和外部渲染器同时开工。

### 阶段 0：基线、契约与关键技术验证

- 固定当前真实媒体测试集、硬件档位和性能基线。
- 将当前首帧指标改为真实交付语义，建立分层呈现指标。
- 明确 Provider、Session、Command、Capability、FrameLease、DisplayOutputInfo 的数据契约。
- 明确 SessionId、MediaId、Epoch、TimelineId、SurfaceGeneration 和 DeviceGeneration。
- 建立威胁模型、依赖 SBOM 和诊断隐私规则。
- 定义各硬件档位的验收 Profile、绝对预算和回归预算。
- 保留当前 FFmpeg/LAV 行为作为对照。

完成四个最小技术验证，不提前承诺完整功能：

1. SwapChainPanel 的 waitable、Present 统计和多屏可观测性；
2. SDR/HDR 交换链、颜色空间和跨屏能力变化；
3. FFmpeg D3D11VA 到自有 Renderer 的最小 FrameLease；
4. LAV D3D11 Native 到自定义 Sink 的最小格式、Allocator 和生命周期验证。

若第 4 项验证失败，LAV 保留 BGRA 兼容路线，不影响 Native 路线继续实施。

### 阶段 1：包装现有路线

- 将当前 FFmpeg 和 LAV 包装为 Provider，不改变默认行为。
- 抽出选择策略、三层能力模型和状态迁移。
- 把“用 FFmpeg 打开当前项”升级为“用其他路线打开”。
- 加入统一 PipelineInfo、Observed 管线和基础指标。
- 为手动路线切换实现 prepare/commit/abort 或明确的不可并存降级流程。

### 阶段 2：会话、命令、状态机与主时钟

- 建立 SessionId/Epoch/CommandId、分维状态机和命令取消关系。
- 使用统一 64 位时间戳、TimelineId 和音频设备主时钟。
- 建立音频预滚动、暂停/seek 清理和渐进同步校正。
- 为打开、probe、读取和 seek 加入 `AVIOInterruptCB` 或等价取消。
- 用虚拟时钟和虚拟输出建立确定性状态机与竞争测试。

### 阶段 3：有界管线、EOF、呈现调度与诊断

- 拆清 demux、decode、audio、video scheduler 和 presenter 的执行边界。
- 建立有界队列、背压、独立取消和完整 EOF drain。
- 实现 HomePlayer 输出的独立 Video Scheduler、分层呈现指标和丢帧原因。
- 加入结构化 Trace、虚拟设备和命令重放。
- 外部输出只适配诊断，不接入 HomePlayer 二次调度。

### 阶段 4：统一 GPU 帧、颜色输出与零拷贝

- 实现 CPU/GPU FrameLease、DeviceGeneration 和资源归还语义。
- VideoPresenter 增加 GPU 输入，保留 BGRA 输入。
- 先实现 Native 的 YUV 上传和 D3D11VA 最小路径。
- 实现显示输出快照、动态显示变化和明确的 SDR/HDR 回退。
- 在技术验证通过后实现 LAV D3D11 Sink，先 NV12，再 P010 和动态格式。
- 用零拷贝等级和实际拷贝事件验证管线，不只检查功能名称。

### 阶段 5：精确 seek、打开体验与恢复

- 完成两阶段精确 seek、open GOP、音频 priming、字幕重建和统一预滚动。
- 加入有界首帧优先、SMB 分级预读、下一集预探测/预打开和异常时间戳修复。
- 完善设备变化、SMB 中断、连续切集和看门狗恢复。
- 验证 demux EOF、输出 drain 和最后一帧/最后音频的结束语义。

### 阶段 6：libplacebo 高质量输出

- 先 D3D11 后端、既有显示输出契约和基础色彩正确性。
- 加入性能/平衡/高质量预设。
- 再验证 HDR 色调映射、去色带、去隔行和高级缩放。
- Basic Renderer 始终保留，IVTC 和 AI 模块另行评估。

### 阶段 7：外部渲染器与其他 Provider

- 先用 MPC VR/madVR 做外部效果与性能参照。
- 按需求实现 MadVROutput：原生窗口、运行时截图能力探测、字幕和设置入口；初版不承诺完整 WinUI 叠层和内部渲染指标。
- 对 mpv 同时评估原生窗口与 libmpv render API。
- 根据 A/B 数据决定 Flyleaf 或 mpv 是否值得正式加入。
- 最终保持一个默认主路线、一个兼容路线和少量有明确价值的可选路线，不以数量为目标。

## 19. 验收标准

### 19.1 验收 Profile 与统计协议

阶段 0 必须为每个硬件档位和路线建立版本化验收 Profile，至少包含：

- 硬件、驱动、OS、显示器、刷新率和 SDR/HDR 环境；
- 媒体测试集版本；
- 首帧、seek、音画偏差、underrun、恢复时间和资源的绝对预算；
- 相对上一稳定版本的回归预算；
- 观测层级和统计可信要求。

没有填写绝对预算、样本数或观测层级的验收不得判定通过。

默认最低统计协议：

- 冷启动和热启动分别至少 30 次有效打开；
- seek 每个场景至少 100 个有效样本；
- 报告样本数、P50/P95/P99、失败数和 `Unknown` 数；
- 不把取消、失败或无法观测的样本静默从结果中删除；
- 性能回归超过 Profile 预算时，即使平均 CPU 更低也不能通过。

### 19.2 契约与状态机测试

每条 Provider 都必须通过统一测试：打开、播放、暂停、seek、停止、EOF、连续切集、轨道与字幕、能力真实性和失败语义。

状态机测试还要覆盖：

- 非法状态命令；
- 命令接受与完成的区别；
- 命令取消和最后一个 CommandId 胜出；
- Epoch、SurfaceGeneration 和 DeviceGeneration 隔离；
- 恢复次数上限和旧事件丢弃；
- 重复 Stop/Close 和异常路径幂等；
- seek 中切集、打开中取消和设备恢复中关闭。

### 19.3 真实媒体矩阵

基础矩阵覆盖 H.264、HEVC、AV1、1080p、4K60、8/10bit、HDR、VFR、ASS/PGS、多音轨、异常时间戳、损坏文件和 SMB。

按产品声明逐步增加：

- HLG、HDR10+、Dolby Vision 的支持或明确降级；
- 4:2:2、4:4:4、12-bit；
- 隔行、混合帧率、telecine；
- SAR/DAR、裁剪、旋转和动态分辨率变化；
- 多声道和非常规声道掩码；
- 无音频、音频时钟不可用和未知时长输入；
- forced/default 字幕和内嵌字体附件；
- open GOP、缺失 PTS 和 discontinuity；
- 多屏 SDR/HDR、DPI 变化和 VRR；
- SMB 凭据失效、断网恢复和文件替换。

不支持的格式必须验证能力声明和失败语义，不要求所有格式都在首版可播放。

### 19.4 可重放与图像回归

- 使用虚拟时钟、虚拟音频和虚拟呈现器重放命令序列。
- 对 seek、颜色矩阵、范围、HDR 降级和色彩处理执行帧哈希或容差图像比较。
- 对损坏媒体、字幕和 demux 输入在隔离进程中执行模糊测试。
- 结构化 Trace 能解释首帧、seek、丢帧和同步校正的完整过程。
- 指标无法观测时必须显示 `Unknown` 及原因。

### 19.5 零拷贝与颜色输出验证

管线必须显示实际路径，并验证：

- 无未声明的每帧 GPU→CPU 回读；
- 无未声明的每帧 CPU BGRA 转换与重复上传；
- 零拷贝等级与实际纹理路径一致；
- 跨设备共享、复制和同步成本单独记录；
- 纹理生命周期和 GPU 完成同步正确；
- 连续 seek 和切集无显存/非托管内存持续增长；
- 交换链格式、颜色空间和 DisplayOutputInfo 与当前显示一致；
- 跨屏和显示能力变化后能恢复或明确降级。

### 19.6 长稳与设备测试

每个主路线至少完成 2 小时长稳；发布候选的默认路线至少完成 8 小时 soak。每个路线至少执行：

- 200 次连续 seek；
- 100 次连续切集；
- 50 次暂停/恢复和逐帧组合；
- 适用时的音轨/字幕切换和设备重建。

验收必须满足：

- 音画偏差不持续漂移，稳态和漂移均在 Profile 预算内；
- seek 记录到约定观测层级的 P50/P95/P99；
- 反复暂停、seek、逐帧和切集无死锁；
- 音频设备断开和 GPU 重建后可恢复或进入明确失败状态；
- 看门狗超时和恢复失败能进入明确状态并留下 Trace；
- 预热后内存、句柄、纹理和租约数量回到 Profile 容差内，不存在持续正向增长趋势；
- 原生输出下截图、字幕和全屏行为与能力声明一致。

### 19.7 对比有效性与回退

性能改进必须同时满足：

- 相同或已声明差异的质量目标下可重复；
- 无明显色彩、字幕或同步回退；
- 不以牺牲兼容路径为代价；
- 统计包含失败、取消和 `Unknown`，不只比较成功样本；
- 失败时可返回当前稳定路径，且回退本身有超时和资源验收。

## 20. 最终形态

HomePlayer 最终不是“内置很多引擎的播放器”，而是：

> 一个由 HomePlayer 自己掌握会话、命令、时间线、帧所有权、能力、状态和诊断的播放平台。原生 FFmpeg 与 DirectShow 提供不同内核，HomePlayer Basic 与 libplacebo 提供统一自有渲染，madVR/MPC VR 提供独立 DirectShow 输出，其他完整引擎只在实测证明价值后加入。

统一不意味着强迫所有引擎使用同一种线程、时钟或呈现实现。平台统一的是用户语义、资源边界、能力真实性和可诊断性；各 Provider 保留适合自身的内部执行模型。

这样既能保留现有稳定性，也能逐步获得可验证的零拷贝、高级画质和路线选择能力，而不会被某一第三方引擎、宿主模型或许可证绑定。
